D1. Com base na história do Hudson e do Jenkins, explique por que a governança de um projeto open source importa para uma empresa que vai depender dele, como a Carparts.
(118 palavras)
O Hudson nasceu em 2004 dentro da Sun, criado por um programador cansado de ver o build quebrar. Quando a Oracle comprou a Sun, surgiu uma briga pelo controle da marca e da infraestrutura do projeto, e em 2011 a comunidade decidiu migrar para o nome Jenkins. O Hudson foi perdendo força até ser descontinuado. Isso mostra que um projeto open source só é confiável enquanto tiver uma comunidade ativa por trás — não basta o código existir. Por isso, antes de adotar uma ferramenta como o Jenkins, a Carparts deveria olhar quem mantém o projeto, com que frequência ele recebe atualizações e se está sob uma fundação neutra, para não depender de algo que pode ser abandonado.

D2. Diferencie Integração Contínua, Entrega Contínua e Implantação Contínua. Qual delas a Carparts deve adotar primeiro, considerando a exigência de aprovação registrada das montadoras?
(97 palavras)
Integração Contínua é integrar o código ao repositório principal com frequência, sempre validado por testes automáticos. Entrega Contínua vai um passo além: o software fica pronto para ir pra produção a qualquer momento, mas alguém decide quando publicar. Implantação Contínua tira esse “alguém”: tudo que passa nos testes já vai direto pra produção, sem aprovação manual. Como as montadoras exigem saber quem aprovou cada publicação, a Carparts deveria adotar primeiro CI e depois Entrega Contínua, com uma etapa de aprovação manual no pipeline. Implantação Contínua pura não funcionaria aqui, porque elimina exatamente o controle que estão pedindo.

D3. Descreva a arquitetura controller/agents do Jenkins e justifique por que o nó interno deve ter 0 executores. Onde você colocaria os agents Windows e Linux da Carparts?
(114 palavras)
O controller é o cérebro do Jenkins: decide quando e onde cada build roda, guarda credenciais, histórico e configuração. Os agents são as máquinas ou contêineres que realmente executam as tarefas, e os executores são as “vagas” de trabalho dentro de cada agent. O nó interno do controller deve ficar com 0 executores porque rodar builds ali expõe dados sensíveis e disputa recursos com o próprio serviço que está coordenando tudo. Para a Carparts, faz sentido ter um agent Linux com Docker pra rodar a API e gerar as imagens, um agent Windows pra partes que dependem desse sistema, e agents temporários na Azure pra absorver picos de demanda sem gastar além do orçamento.

D4. Compare instalar o Jenkins via MSI no Windows, via pacote apt no Ubuntu e via contêiner Docker para o laboratório da turma. Aponte vantagens e riscos de cada opção.
(108 palavras)
Instalar via MSI no Windows é familiar pra quem já usa o sistema, mas exige configurar Java e conta de serviço manualmente, e é mais chato de desfazer depois. Instalar via apt no Ubuntu se integra bem ao systemd e facilita atualizações, mas também depende da versão certa do Java e de manter a chave do repositório atualizada. Já a instalação via Docker é a mais prática pra laboratório: é descartável, a versão fica fixada na tag da imagem, e atualizar é só trocar essa tag. O cuidado principal é não usar bind mount com permissão errada e nunca montar o socket do Docker do host sem necessidade.

D5. Explique o Jenkinsfile de CI/CD da seção 06: o papel de agent none no topo, de when, do input fora de um agent e do bloco post. O que aconteceria se o input estivesse dentro de um stage com agent?
(123 palavras)
Usar agent none no topo do pipeline permite que cada stage escolha seu próprio agent — por exemplo, um contêiner Node pra rodar os testes e outro agent pra montar a imagem Docker. A diretiva when { branch 'main' } garante que publicação e deploy só aconteçam na branch principal, enquanto PRs e outras branches passam só pela parte de integração. O input fica fora de um bloco com agent justamente pra não travar um executor enquanto espera alguém aprovar a publicação. Já o post trata o que acontece depois do pipeline, avisando a equipe em caso de sucesso ou falha. Se o input estivesse dentro de um stage com agent, esse executor ficaria preso até alguém aprovar, travando outros builds na fila.

D6. Com a aposentadoria dos plugins Azure em 2024, como integrar Jenkins e Azure com segurança? Discuta service principal × identidade gerenciada, escopo mínimo e o risco de abrir a porta 8080.
(117 palavras)
Desde que a Microsoft aposentou os plugins oficiais do Jenkins pra Azure em 2024, a recomendação passou a ser usar a Azure CLI direto nos steps do pipeline. Pra autenticar, dá pra usar um service principal com permissão limitada só ao grupo de recursos da aplicação, guardado como credencial no Jenkins — ou, se o Jenkins estiver rodando dentro da própria Azure, usar identidade gerenciada, que elimina senha. Em qualquer um dos dois casos, o segredo nunca deve aparecer no Jenkinsfile. Deixar a porta 8080 aberta pra qualquer IP na internet é um risco grande, porque expõe a tela de login a ataques; o ideal é usar túnel SSH, Bastion ou um proxy HTTPS com acesso restrito.
