Visão geral e funcionalidades do Jenkins

Conteúdo 6.1 · O que é o Jenkins, o que ele entrega de fábrica, como está organizado por dentro e onde ele se posiciona entre as ferramentas de CI/CD.

O Jenkins é um servidor de automação open source, escrito em Java e distribuído sob licença MIT. Ele recebe um evento (um push no Git, um horário agendado, um clique) e executa uma sequência de tarefas: compilar, testar, analisar, empacotar e implantar. O projeto se descreve como “o servidor de automação open source líder” e sustenta esse papel com um ecossistema de mais de 2.000 plugins.

2.000+plugins no índice oficial (plugins.jenkins.io)
MITlicença do núcleo, escrito em Java
26,5 milestrelas do repositório jenkinsci/jenkins no GitHub (set/2026)
2.568.3versão LTS vigente · semanal 2.581 (set/2026)

Funcionalidades principais

núcleo

Integração e entrega contínuas

Dispara builds a cada mudança no repositório, publica relatórios de teste e artefatos e pode seguir até a implantação em homologação e produção.

pipeline

Pipeline como código

O processo de entrega fica num Jenkinsfile versionado junto com a aplicação, revisado em pull request como qualquer código.

ecossistema

Plugins

Integrações com Git, GitHub, Docker, Kubernetes, Maven, npm, SonarQube, Slack, nuvens públicas e ferramentas de teste.

escala

Builds distribuídos

Um controller coordena vários agents (Linux, Windows, macOS, contêineres, VMs na nuvem) que executam os jobs em paralelo.

segurança

Credenciais e permissões

Cofre de credenciais (senhas, tokens, chaves SSH, certificados) injetadas no build sem aparecer no log; autorização por matriz de permissões.

operação

Configuração como código

O plugin JCasC descreve o controller inteiro num arquivo YAML, o que torna a instalação reprodutível e auditável.

Instalação simples, interface web

O Jenkins é uma aplicação Java autocontida: roda em Windows, Linux, macOS e outros Unix, em contêiner Docker ou no Kubernetes. A configuração é feita pela interface web, que valida os campos e mostra ajuda contextual (ícone “?”).

Arquitetura: controller, nós, agents e executores

Controller

É o próprio serviço Jenkins, onde ele está instalado: o “cérebro” que decide como, quando e onde executar as tarefas, além de guardar configuração, autorização e histórico.

Node (nó)

Máquina que participa do ambiente Jenkins e é capaz de executar pipelines. O Jenkins monitora espaço em disco, memória e tempo de resposta de cada nó e o coloca offline se passar dos limites.

Agent

Processo Java pequeno (um jar de cerca de 170 KB) que se conecta ao controller e executa as tarefas. As ferramentas do build (JDK, Node.js, Docker CLI) ficam instaladas no agent ou num contêiner.

Executor

“Vaga” de execução dentro de um nó, na prática uma thread. O número de executores define quantos stages podem rodar ao mesmo tempo naquele nó.

Não rode builds no controller

A documentação oficial desaconselha executar tarefas no nó interno (built-in node) por motivos de segurança, desempenho e escalabilidade: um build malicioso ou pesado ali teria acesso ao JENKINS_HOME. Configure 0 executores no nó interno e use agents.

02

História: do Hudson ao Jenkins

Conteúdo 6.1 · Um projeto que nasceu para resolver um problema pessoal de um programador, virou padrão de mercado e passou por uma disputa de marca que definiu seu modelo de governança.

Em 2004, Kohsuke Kawaguchi, programador Java da Sun Microsystems, cansou de receber ligações de colegas dizendo que o código que ele tinha acabado de enviar havia quebrado o build. Em vez de prestar mais atenção manualmente, decidiu escrever um programa que compilasse e testasse tudo automaticamente a cada mudança. Esse programa se chamou Hudson.

  • 2004
    Nasce o Hudson na Sun MicrosystemsKawaguchi cria a ferramenta para automatizar build e integração e parar de “quebrar o build” dos colegas.
  • 2005
    Primeira versão pública (fevereiro)O Hudson ganha espaço como alternativa ao CruiseControl e a outros servidores de build.
  • 2008
    Duke’s Choice Award (JavaOne, maio)Prêmio na categoria Developer Solutions consolida a popularidade do Hudson na comunidade Java.
  • 2010
    Oracle compra a Sun e surgem os atritosA comunidade questiona o controle da infraestrutura do projeto; em dezembro a Oracle pede o registro da marca “Hudson”.
  • 2011
    A comunidade vota e o projeto vira JenkinsProposta de renomear em 11/01, aprovada por ampla maioria em 29/01. A Oracle anuncia que seguirá com o Hudson (01/02) e a primeira versão com o nome Jenkins sai em 02/02/2011. Kawaguchi recebe o O’Reilly Open Source Award e, no mesmo ano, sua empresa InfraDNA é adquirida pela CloudBees, onde ele depois se torna CTO.
  • 2012
    Hudson vai para a Eclipse FoundationA Oracle doa o Hudson à Eclipse Foundation, enquanto o Jenkins concentra a maior parte dos contribuidores.
  • 2016
    Jenkins 2 (20 de abril)O plugin Pipeline passa a vir por padrão: o processo de entrega agora pode ser escrito como código, numa DSL baseada em Apache Groovy.
  • 2017
    Hudson declarado obsoleto · Blue OceanEm fevereiro o Hudson é oficialmente aposentado. No Jenkins, o Blue Ocean moderniza a visualização de pipelines (hoje ele não recebe novas funcionalidades).
  • 2018
    Jenkins X (março)Projeto separado voltado a CI/CD nativo em Kubernetes, que depois segue caminho independente.
  • 2019
    Continuous Delivery Foundation (março)O Jenkins é projeto fundador da CDF, sob a Linux Foundation. Em agosto de 2020 alcança o status de projeto graduado.
  • 2024
    Microsoft encerra o suporte aos plugins Azure (29/02)A recomendação passa a ser integrar via Azure CLI; alguns plugins seguem mantidos pela comunidade Jenkins (ver seção 08).
  • 2026
    Java 21 ou 25 obrigatórioA partir da LTS 2.555.1 (abril/2026), controller e agents precisam de Java 21 ou 25. Em setembro, a LTS vigente é a 2.568.3.

O que essa história ensina

Governança comunitária

O fork mostrou que um projeto open source pertence, na prática, a quem o mantém. O Jenkins tem hoje governança aberta e documentada.

Automação nasce da dor

O Hudson não surgiu de uma teoria, e sim de um problema real de integração. É o mesmo raciocínio do lead time de 11 dias da Carparts.

Evolução para código

Do job configurado por formulário (Freestyle) ao Jenkinsfile versionado: a mesma transição que o mercado fez para “tudo como código”.

03

Metodologia: CI, CD e pipeline como código

Conteúdo 6.1 · O Jenkins é uma ferramenta; a metodologia é da equipe. Aqui ligamos cada prática de integração e entrega contínuas ao recurso do Jenkins que a sustenta.

CI

Integração Contínua

Cada desenvolvedor integra seu trabalho ao tronco principal com frequência (pelo menos diariamente). Cada integração é verificada por um build automatizado com testes, para detectar erros o quanto antes.

CD

Entrega Contínua

O software fica sempre pronto para ir à produção. O pipeline leva cada mudança até um ambiente de homologação; a ida para produção é uma decisão de negócio, com um clique.

CD

Implantação Contínua

Passo além: toda mudança que passa em todos os testes vai para produção automaticamente, sem aprovação manual.

  1. Commitpush ou pull request
  2. Buildcompilação e dependências
  3. Testesunitários e integração
  4. Qualidadelint, cobertura, segurança
  5. Artefatoimagem ou pacote versionado
  6. Homologaçãodeploy e smoke test
  7. Aprovaçãogate manual (CD)
  8. Produçãodeploy e monitoramento

Princípios do pipeline como código

Versionado e revisado

O Jenkinsfile passa por pull request. Mudar o processo de entrega deixa rastro, autor e justificativa.

Construa uma vez, implante muitas

O mesmo artefato (por exemplo, a imagem carparts-api:57) é promovido de homologação para produção. Nada é recompilado no meio do caminho.

Falhe cedo

Etapas baratas e rápidas (lint, testes unitários) vêm antes das caras (testes de integração, deploy).

Agentes efêmeros e reprodutíveis

Cada build roda num contêiner ou VM limpa. “Na minha máquina funciona” deixa de ser argumento.

Segredos fora do código

Tokens e senhas ficam no cofre de credenciais e entram via credentials() ou withCredentials, mascarados no log.

Gates explícitos

Critérios de qualidade (cobertura mínima, zero vulnerabilidade crítica, aprovação humana) viram etapas do pipeline, e não combinados verbais.

Como medir se está funcionando: métricas DORA

O programa de pesquisa DORA acompanha hoje cinco métricas de desempenho de entrega, agrupadas em vazão (as três primeiras) e instabilidade (as duas últimas). A pesquisa mostra que velocidade e estabilidade não são opostas: equipes de alto desempenho vão bem nas cinco.

Lead timeda mudança: do commit até a implantação em produção (Carparts hoje: 11 dias)
Frequênciade implantação: quantas implantações num período
Recuperaçãotempo para se recuperar de uma implantação com falha
Falhastaxa de mudanças que exigem intervenção imediata após a implantação
Retrabalhotaxa de implantações não planejadas causadas por incidentes em produção
Jenkinscada execução registra duração, resultado, commit e horário — matéria-prima dessas métricas
O Jenkins mede para você

Cada execução guarda duração, resultado, autor do commit e horário. Com esse histórico dá para calcular lead time e taxa de falha sem planilhas manuais — é o ponto de partida da atividade prática desta aula.

Comandos oficiais para a linha LTS em Ubuntu/Debian (válidos para Ubuntu 24.04 e para o WSL 2). A chave do repositório é renovada periodicamente; confira o nome do arquivo .key na página de instalação antes de colar.

bash · Ubuntu 24.04 / Debian
# 1) Java 21
sudo apt update
sudo apt install fontconfig openjdk-21-jre
java -version

# 2) Repositório LTS do Jenkins
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null

# 3) Instalar e iniciar
sudo apt update
sudo apt install jenkins
sudo systemctl enable jenkins
sudo systemctl start jenkins
sudo systemctl status jenkins

# 4) Senha inicial
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

Para trocar a porta, crie um override do systemd em vez de editar arquivos do pacote:

bash · trocar a porta para 8081
sudo systemctl edit jenkins
# no editor, acrescente:
# [Service]
# Environment="JENKINS_PORT=8081"
sudo systemctl restart jenkins

Red Hat, Rocky e Fedora usam o repositório https://pkg.jenkins.io/rpm-stable/ (LTS) com dnf; os comandos systemctl são os mesmos.

O arquivo jenkins.war roda em qualquer sistema com Java 21 ou 25. É ótimo para testar uma versão, mas não cria serviço nem reinicia sozinho.

bash ou PowerShell
# baixe o jenkins.war da linha LTS em https://www.jenkins.io/download/
java -jar jenkins.war                  # sobe na porta 8080
java -jar jenkins.war --httpPort=9090  # porta alternativa

# o JENKINS_HOME padrão é ~/.jenkins (Linux) ou %USERPROFILE%\.jenkins (Windows)

Forma mais rápida de ter um Jenkins funcionando, usando a imagem oficial com Java 21 e um volume nomeado para os dados:

bash · Docker
docker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  --restart=on-failure \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts-jdk21

docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

Evite bind mount de uma pasta do host em /var/jenkins_home: o usuário do contêiner (uid 1000) pode não ter permissão. Prefira volume nomeado. A versão completa, com Docker-in-Docker, está na seção 07.

Checklist pós-instalação

Segurança

  • Nó interno com 0 executores (Manage Jenkins → Nodes → Built-In Node).
  • Autorização por matriz (plugin Matrix Authorization Strategy); nada de acesso anônimo.
  • HTTPS por proxy reverso (Nginx, Apache, Application Gateway) em vez de expor a 8080.
  • Acompanhar os Security Advisories e atualizar plugins com aviso de vulnerabilidade.

Operação

  • Backup do JENKINS_HOME (jobs, credenciais criptografadas, histórico).
  • Descarte de builds antigos (buildDiscarder) para o disco não encher.
  • Pelo menos um agent configurado antes do primeiro pipeline.
  • Testar a atualização de LTS num ambiente de cópia antes de produção.

Pipeline de projetos: Jenkinsfile para CI/CD

Conteúdo 6.2 · Pipeline é um conjunto de plugins que permite modelar a entrega contínua como código. Aqui estão os conceitos, as duas sintaxes, as diretivas e um Jenkinsfile completo de CI/CD.

Um Jenkinsfile é um arquivo de texto, salvo na raiz do repositório, que descreve o pipeline. Por estar no controle de versão, ele cria uma trilha de auditoria do processo de entrega e é revisado como qualquer código.

pipeline

Pipeline

Modelo definido pelo usuário do processo de CD: build, teste, entrega.

agent / node

Agent

Onde o pipeline (ou um stage) roda: aloca executor e workspace.

Jenkinsfile completo de CI/CD: Carparts API

Projeto Node.js com Dockerfile. O pipeline roda num Multibranch Pipeline: em qualquer branch ou PR executa a parte de CI; na main publica a imagem, implanta em homologação, pede aprovação e implanta em produção.

  1. Qualidadenpm ci, lint e testes em contêiner Node
  2. Imagemdocker build com tag do build
  3. Publicaçãopush para o registro (só main)
  4. Homologaçãodeploy + smoke test
  5. Aprovaçãoinput, sem prender executor
  6. Produçãomesma imagem, promovida
Jenkinsfile · carparts-api
pipeline {
    agent none                                  // cada stage escolhe seu agent

    options {
        timeout(time: 45, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '20'))
        disableConcurrentBuilds()
    }

    environment {
        APP      = 'carparts-api'
        REGISTRY = 'carpartsacr.azurecr.io'
        TAG      = "${env.BUILD_NUMBER}"
    }

    stages {
        stage('Qualidade') {
            agent { docker { image 'node:22-alpine' } }
            environment { npm_config_cache = "${env.WORKSPACE}/.npm" }
            steps {
                sh 'npm ci'
                sh 'npm run lint'
                sh 'npm test'                   // gera reports/junit.xml
            }
            post {
                always { junit allowEmptyResults: true, testResults: 'reports/*.xml' }
            }
        }

        stage('Imagem e publicação') {
            agent { label 'linux && docker' }
            steps {
                sh 'docker build -t $REGISTRY/$APP:$TAG .'
                script {
                    if (env.BRANCH_NAME == 'main') {
                        docker.withRegistry("https://${REGISTRY}", 'acr-credenciais') {
                            docker.image("${REGISTRY}/${APP}:${TAG}").push()
                        }
                    }
                }
            }
        }

        stage('Deploy homologação') {
            when { branch 'main' }
            agent { label 'linux' }
            steps {
                sh './scripts/deploy.sh homologacao $TAG'
                sh 'curl --fail --retry 5 --retry-delay 10 https://hml.carparts.example/health'
            }
        }

        stage('Aprovação') {
            when { branch 'main' }
            steps {                              // sem agent: não ocupa executor esperando
                timeout(time: 1, unit: 'DAYS') {
                    input message: "Publicar ${APP}:${TAG} em produção?", ok: 'Aprovar'
                }
            }
        }

        stage('Deploy produção') {
            when { branch 'main' }
            agent { label 'linux' }
            steps {
                sh './scripts/deploy.sh producao $TAG'
            }
        }
    }

    post {
        success { echo "Entrega de ${APP}:${TAG} concluída." }
        failure {
            mail to: 'devops@carparts.example',
                 subject: "Falhou: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                 body: "Detalhes em ${env.BUILD_URL}"
        }
    }
}
Por que aspas simples em sh '... $TAG'?

Com aspas simples, quem expande $TAG é o shell do agent, a partir da variável de ambiente. Com aspas duplas, o Groovy interpola antes. Para segredos, use sempre aspas simples: a interpolação Groovy pode vazar a senha no log e na linha de comando do processo.

Multibranch + webhook: disparo a cada push

  1. No Jenkins: New Item → Multibranch Pipeline → Branch Sources: GitHub → credencial (token do GitHub) → URL do repositório → Script Path: Jenkinsfile.
  2. No GitHub: Settings → Webhooks → Add webhook → Payload URL https://jenkins.carparts.example/github-webhook/ → eventos de push e pull request.
  3. Cada branch e cada PR com Jenkinsfile vira um pipeline; o resultado aparece como check no pull request.
  4. Sem URL pública (laboratório local)? Use triggers { pollSCM('H/5 * * * *') } temporariamente.
Reaproveitamento entre projetos

Quando vários repositórios repetem os mesmos stages, extraia-os para uma Shared Library (repositório Git com funções Groovy) e carregue com @Library('carparts-lib') _ no topo do Jenkinsfile.

Laboratório oficial: Jenkins + Docker-in-Docker

O tutorial de instalação do jenkins.io usa dois contêineres na mesma rede: o Jenkins (com o Docker CLI instalado) e um docker:dind que executa os comandos Docker dos pipelines, protegido por TLS.

# 2) Docker-in-Docker
docker run \
  --name jenkins-docker \
  --rm \
  --detach \
  --privileged \
  --network jenkins \
  --network-alias docker \
  --env DOCKER_TLS_CERTDIR=/certs \
  --volume jenkins-docker-certs:/certs/client \
  --volume jenkins-data:/var/jenkins_home \
  --publish 2376:2376 \
  docker:dind \
  --storage-driver overlay2

# 3) construir a imagem do Jenkins (Dockerfile na aba ao lado)
docker build -t myjenkins-blueocean:2.568.3-1 .

# 4) subir o Jenkins
docker run \
  --name jenkins-blueocean \
  --restart=on-failure \
  --detach \
  --network jenkins \

  --env DOCKER_CERT_PATH=/certs/client \
  --env DOCKER_TLS_VERIFY=1 \

Pipeline que usa só a Azure CLI: login com o service principal, build da imagem no Azure Container Registry e atualização de um Web App for Containers de homologação. O agent precisa ter a Azure CLI instalada.

Jenkinsfile · deploy na Azure via Azure CLI
pipeline {
    agent { label 'linux && azure-cli' }

    environment {
        RG              = 'rg-carparts'
        ACR             = 'carpartsacr'
        WEBAPP          = 'carparts-api-hml'
        IMAGE           = "carparts-api:${env.BUILD_NUMBER}"
        AZURE_TENANT_ID = credentials('azure-tenant-id')
    }

    stages {
        stage('Login na Azure') {
            steps {
                withCredentials([usernamePassword(credentialsId: 'azure-sp',
                        usernameVariable: 'AZURE_CLIENT_ID',
                        passwordVariable: 'AZURE_CLIENT_SECRET')]) {
                    sh 'az login --service-principal --username "$AZURE_CLIENT_ID" --password "$AZURE_CLIENT_SECRET" --tenant "$AZURE_TENANT_ID" --output none'
                }
            }
        }

        stage('Build da imagem no ACR') {
            steps {
                sh 'az acr build --registry "$ACR" --image "$IMAGE" .'
            }
        }

        stage('Deploy homologação') {
            steps {
                sh '''
                    az webapp config container set \
                      --resource-group "$RG" --name "$WEBAPP" \
                      --container-image-name "$ACR.azurecr.io/$IMAGE" \
                      --container-registry-url "https://$ACR.azurecr.io"
                    az webapp restart --resource-group "$RG" --name "$WEBAPP"
                '''
            }
        }

        stage('Smoke test') {
            steps {
                sh 'curl --fail --retry 5 --retry-delay 15 "https://$WEBAPP.azurewebsites.net/health"'
            }
        }
    }

    post {
        always { sh 'az logout || true' }
    }
}

Dois pré-requisitos do lado Azure: o Web App precisa de permissão AcrPull no registro (identidade gerenciada do app) e a assinatura precisa permitir ACR Tasks para o az acr build. Se ACR Tasks não estiver disponível, troque o stage por az acr login --name "$ACR" + docker build + docker push. Para Azure Container Apps, o deploy equivalente é az containerapp update --name ... --resource-group ... --image ....

    Equipe de 1 designer + 4 desenvolvedores, parque misto com 2 estações Windows 11 + WSL 2 e 2 Ubuntu 24.04. O lead time atual é de 11 dias entre o commit e a produção: builds manuais, testes rodados “quando dá” e deploy feito por uma única pessoa.

    O portal de pedidos B2B tem uma API Node.js em contêiner e um front-end web. As montadoras clientes passaram a exigir rastreabilidade: saber qual commit está em produção e quem aprovou a publicação.

    restrições

    O que a diretoria definiu

    • Servidor de CI/CD Jenkins autogerenciado (dados do ERP ficam on-premises).
    • Homologação na Azure (App Service ou Container Apps + ACR).
    • Orçamento de nuvem para CI/CD de US$ 150/mês (o de IA, US$ 300/mês, continua separado).
    • Aprovação registrada antes de qualquer publicação em produção.
    • Meta: lead time de no máximo 2 dias em até dois meses.

    • Segredo (senha, token, appId + password) commitado no repositório ou visível no log do build.
    • Builds executando no nó interno do controller.
    • Jenkins acessível pela internet sem autenticação ou com a porta 8080 aberta para qualquer origem.
    • Publicação em produção sem registro de aprovação, ou imagem recompilada entre homologação e produção.
    • Entrega sem evidência de execução real (prints, logs ou link do repositório) ou com cópia de outro grupo.
